# Standalone Trivy advisory scanner

This future-use prototype is separate from the updater and deployment. `python3 advisory_trivy.py candidate IMAGE` captures a local image ID; `python3 advisory_trivy.py running CONTAINER` captures a running container's image and container IDs, and checks them again after scanning. It exports the captured immutable image to a private temporary archive and scans that archive with the locally available Trivy image pinned to `sha256:790fd66d1697395d8693d1acaa1ea702406a20f109b6fc7bac8db623eca6c06c`. No image is pulled. The temporary scanner container has no Docker socket, Docker credentials, or production container mounts; it uses a read-only root and archive, dropped capabilities, and temporary writable cache. The Trivy process needs network access to download vulnerability databases. The temporary archive contains the image's contents and is deleted after the scan; ensure the local temporary filesystem is private and has enough space. Host root and the Docker daemon can access it.

Output is a deliberately limited JSON report of HIGH and CRITICAL vulnerabilities. Exit 0 means none were reported by this scan, 1 means findings, and 2 means an error or untrusted/incomplete report. Input capture, scanner exit, report schema, image ID, vulnerability fields, and running-container identity are checked fail closed. Docker/Trivy stderr is suppressed to avoid disclosing credentials. No credentials, full inspect output, image configuration, or raw Trivy report are emitted. Candidate references are resolved once before export; later tag movement cannot change what is scanned. Running-container checks do not guarantee continued identity after the final check.

The archive is mode 0644 so the unprivileged scanner can read its bind mount; its temporary parent directory remains mode 0700. Before scanning, the wrapper verifies the saved config hash against the inspected image ID, or verifies the OCI index/manifest digest chain to the saved config when Docker identifies the image by an OCI descriptor. Trivy's archive-derived `Metadata.ImageID` can differ from Docker's image ID; it is validated as a digest but is not used as the binding. The verification relies on the local Docker daemon's image export and is not a separate verification of every layer.

The scanner intentionally rejects empty `Results` as indeterminate. Database freshness and feed completeness, unsupported image ecosystems, other severities, and runtime changes are not established by a clean report. Trivy downloads its DB into disposable container storage; no freshness timestamp is independently verified. This is an advisory tool, not an admission authority. Test it against representative disposable images and confirm archive support, DB access, scanner version behavior, resource limits and storage policy before operational use. Do not run against production without an explicit operational decision.

Tests: `python -B -m unittest discover -s deployment/firecrawl-updater -p test_advisory_trivy.py`.
