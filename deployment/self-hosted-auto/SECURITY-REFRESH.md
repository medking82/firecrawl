# Automatic image security refresh

`security_refresh.py` rebuilds the three running API images from their immutable local IDs using the Debian 12 security repository. It preserves source, image configuration, database schemas and existing overlay code. It is an OS security updater, not an automatic upstream Firecrawl/Node dependency upgrade. Upstream source/overlay compatibility continues to require a separate reviewed admission path; the previous core-only updater must not run alongside this owner.

Each candidate must preserve its base layers and image configuration, pass the installed transport verifier, have Debian 12 `libbrotli1 >= 1.0.9-2+deb12u1`, and pass an offline Trivy comparison against its running image with the same freshly downloaded DB. Any newly observed HIGH/CRITICAL advisory or severity escalation rejects deployment. Brotli CVE-2026-111497 rejects deployment even if already present in the baseline. Existing findings remain actionable and are not evidence of safety. Java coverage is unsupported and fails closed when identified. New vulnerabilities can lack a vendor fix, and Node/Cargo/application findings are detected but not automatically remediated by this OS updater.

A private fsynced transaction journal preserves exact image IDs, Compose paths, input hashes, container snapshots and checks before stopping any API. There are no schema migrations or runtime env file writes. A short stop barrier closes HTTP endpoints and the in-process monitor scheduler; existing browser sessions, active jobs or connections defer the update, and queues are checked again after all APIs stop. New requests during maintenance can fail and should be retried by clients. The browser manager uses its existing admission marker and thaw watchdog. Candidates start only after that barrier passes.

The recovery timer runs at boot and every minute. While the updater holds its locks recovery does nothing. An interrupted applying/recovering transaction restores all three original images, including when an API container is stopped or missing. Repeated recovery is idempotent. Unknown images or modified input files fail closed and retain the gate rather than overwriting other work. The filesystem, Docker, helper release and private state must survive; recovery cannot repair a lost disk/DB, an unavailable Docker daemon or hostile modifications. Recovery starts after the user systemd manager and Docker are available, not before Docker auto-starts containers. Full machine power-loss testing has not been performed; a real Docker fixture verifies SIGKILL checkpoints and lost API containers.

Install the pinned helper release, this directory, and the advisory scanner/owner/notifier in sibling `firecrawl-updater`. Keep state under `~/.local/state/firecrawl-security-refresh` mode 0700. Run `bash install-security-refresh.sh` to replace the old core-only command and service, install the six-hour `firecrawl-update.timer`, enable boot/minute recovery, and validate the new updater before restoring its timer. `firecrawl-security-notify.timer` consumes changed scan/updater reports every ten minutes with `--record-only`, persisting private, deduplicated events under `~/.local/state/firecrawl-advisory/notifications`. Per the user's preference, it does not attempt desktop delivery, email, chat notifications or Codex scheduled tasks. Notification integration is documented in `../firecrawl-updater/notify-README.md`. Keep all rollback images and Compose overlays: running containers reference these private journal paths. There is no automatic image/journal garbage collection.

Validation on Linux: `python3 -B -m unittest test_security_refresh -v`; `python3 -B security_refresh_fixture.py` creates isolated random Redis Compose projects, injects five SIGKILL checkpoints, restores original images, checks Redis and removes fixture resources. It does not touch production.
